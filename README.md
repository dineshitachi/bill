# CHINNATHAMBI TRADERS Billing

A local full-stack billing workspace with a Fastify gateway, a compatibility PowerShell HTTP API, SQLite persistence, password-based authentication, and role checks.

## Run

Install the gateway dependencies once with `npm.cmd install --prefix .\local-api`, then double-click `Start-BillingAI.cmd` to start the local app and open it in your browser. The first run also creates a `Billing AI` shortcut on your Windows Desktop. The launcher reuses a running Fastify gateway or selects a free local port. In VS Code, F5 starts the gateway before opening the browser.

The VS Code launch task is pinned to port 8766 to match its Chrome URL and fails clearly if another service owns that port. The normal launcher still selects a free fallback port and opens the matching URL.

For a dedicated Windows app window, run `Install-BillingAI.cmd`. It adds per-user Desktop and Start Menu shortcuts that open the app in Microsoft Edge app mode and start the local backend. The app files and `billing.sqlite3` remain in this folder; the installer does not copy, reset, or delete billing data. Run `Uninstall-BillingAI.cmd` to remove those shortcuts. To install it as an Edge PWA instead, start the app and use Edge's Apps menu to install the current site.

To start the staged Fastify gateway directly from PowerShell:

```powershell
node .\local-api\server.mjs --port 8766
```

The gateway configures SQLite WAL mode, a 64 MiB page cache, health metrics, checkpoints, and online backups, then proxies the existing API to a loopback-only PowerShell compatibility process. If port 8766 is occupied by a legacy server, the launcher selects another free port. Keep the Node gateway process open while using the app.

This is a phased migration, not a completed Node rewrite. Authentication, business routes, PBKDF2-SHA1 hashes, and DPAPI-protected state still run in the PowerShell compatibility API. The existing database is not yet migrated to AES-GCM or new password hashes; do not remove the PowerShell server until that migration and route parity are separately validated. Optional HTTP/2 requires `BILLING_TLS_KEY` and `BILLING_TLS_CERT`; without those the local gateway uses HTTP/1.1. The gateway rejects cross-origin requests and only enables HSTS when TLS is configured.

The standalone app serves Tailwind from the local `billing-tailwind.css` file; it does not load Tailwind from a browser CDN. After changing Tailwind classes in `bill.html`, regenerate that file from `platform/` with `npm run build:standalone-css`.

On a new installation, create the administrator from the sign-in screen. New passwords must be 6-20 characters; longer, unique passwords are recommended. Admins can create admin or staff accounts from Admin Panel → Team Access; administrators and staff share the same billing records on this installation, while only admins can delete catalog records or change business settings and account access. Users sign in with a username. Registration requires a unique username, while email is optional.

If accounts already exist and you need another administrator, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server.ps1 -CreateAdmin` in PowerShell. This prompts for the new account details and a masked password, then appends the admin without replacing existing accounts. Restart the normal server command afterward if it was stopped.

Admins can reset passwords from Admin Panel → Team Access using the Reset password action beside an account. Passwords must be 6-20 characters. If the only administrator is locked out, run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server.ps1 -CreateAdmin` in PowerShell to create a recovery administrator.

For a visible top-level control account, stop the server and run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\server.ps1 -CreateOwner`. The single Master Control account can create role profiles and Admin Control/Staff accounts, view the security audit feed, and reset passwords. Admin Control accounts can create Staff role profiles, manage, revoke, or delete Staff accounts, and add industry types. Master Control sign-ins, privileged API write attempts, account changes, and password resets are recorded without request bodies or passwords. Master Control is listed in Team Access; it is not hidden or silently recreated.

## Billing, database, and authentication

The GST Billing form includes 30 selectable print designs plus a blank form. The selected design is saved with each invoice and reused when viewing or printing it.

The GST Billing page provides invoice history and a multi-item invoice form. Each invoice stores a `lineItems` array, GST per item, and optional percentage or fixed-amount discount that reduces taxable value before GST; older single-item invoices remain supported. Sales are stored as one atomic server operation, receive a server-assigned invoice number, and update stock and activity together. Admin reports include staff-created sales by invoice date; quotations are excluded from sales totals.

Staff-created billing, inventory, and customer records are synchronized into the shared SQLite-backed workspace and are merged into the admin view automatically; admins do not have to approve each sync. Authenticated foreground sessions poll a monotonic change cursor once per second and fetch an authoritative snapshot only when its version changes, preserving the existing local pending-write merge behavior. Billing, inventory, and accounting are separate views. Invoices record the selected payment mode for receipt/ledger display, while customer receipts remain manually recorded. The GSTIN check validates format locally only: there is no authorized GST portal provider, government registration verification, or e-invoice submission configured. The language selector translates interface text for English, Tamil, Hindi, Telugu, Kannada, Malayalam, Bengali, Marathi, Gujarati, and Punjabi, and voice dictation requests the selected language locale from the browser. The browser serves the localization script as a static asset so language selection is available in both login and the signed-in app.

Successful shared-state mutations append a sequenced event in the same SQLite transaction as the state update. Events contain actor, role, collection, operation, and record count only; record contents, passwords, customer details, and request bodies are excluded. Admin Control sees Staff change events; Master Control sees Admin and Staff events; Staff receives Master update notifications through the shared cursor but cannot inspect control activity. The event buffer retains the latest 1,000 events and returns at most 100 per request; clients detect gaps and recover with a full state snapshot. Privileged API write attempts are separately recorded, including rejected attempts, and are labeled as attempts. This local app binds to `127.0.0.1`; synchronization is between authenticated sessions connected to this host, not across remote devices or networks.

Sales created offline are saved in an IndexedDB outbox and remain visible on that device with a pending number. They receive the official invoice number when the server acknowledges them. Customer and item edits are saved locally and merged by record ID when connectivity returns; admin removals are sent as explicit deletions, and the server rejects staff deletion attempts. The app retries pending work on reconnect and periodically while open. Keep the app open on the device until pending records show as synced. If stock was adjusted while offline on multiple devices, the latest submitted item stock wins; sales themselves are deduplicated and decrement stock only once.

Admins can upload a PNG, JPEG, or WebP company logo from Business Settings by dragging it into the upload zone or selecting a file. The browser resizes it to fit the invoice header, and the shared workspace stores it for staff to use on printed invoices; only admins can replace or remove it. New invoices retain the logo snapshot captured when they are created. Invoices and reports can be exported as Excel-compatible CSV files. WhatsApp sharing opens a prefilled message for the customer's number; the sender must confirm the message in WhatsApp. To attach the full bill, print it or save it as PDF and attach it in WhatsApp. WhatsApp does not send files through a browser link.

The Customers page summarizes billed, received, and pending amounts, includes a pending-only list, and records custom partial payments by cash, UPI, hand/manual, or another method. Payment entries sync through the existing offline outbox. The General navigation includes a Low Stock Alerts page with current available quantities, reorder thresholds, stock value, and direct stock-update actions. Admins can enable browser alerts for new low-stock items and recorded customer payments; browser permission is required on each device. Customer WhatsApp reminders are prepared for review and manual sending; no message is sent without confirmation.

The local server creates `billing.sqlite3` in the project folder. Billing collection snapshots are stored in the `app_state` table, with a row per collection; user accounts (including salted PBKDF2 password hashes) are stored separately in `app_users`. Existing `data.json` and `users.json` files are imported once on first startup; the original JSON files are left untouched as migration backups. Back up `billing.sqlite3` while the server is stopped.

The app provides setup, registration, login, logout, current-user, and admin account-management endpoints under `/api/auth` and `/api/staff`. Authentication uses salted PBKDF2 password hashes, an HTTP-only SameSite=Strict cookie, role checks, sign-in rate limiting, and a fixed eight-hour server-side session. Session token hashes are stored in SQLite; logout, expiry, and password resets revoke sessions. No password or offline authentication profile is stored in browser storage. The login screen accepts sign-in only through the local server, not from a `file:///` URL. The server binds to `127.0.0.1`, so it is intended for this computer and is not a public or multi-device internet service. Remote use requires a separately secured HTTPS host and deployment configuration. SQLite collection snapshots and user-profile records are encrypted with Windows DPAPI for the current Windows user; session metadata and other database fields are not encrypted by the app. Protect the device and database backups with Windows BitLocker or equivalent full-volume encryption. DPAPI-protected records may not be readable under a different Windows account.

The Agent requests page is a human-reviewed intake scaffold shared by staff and admins. Typed reports and optional PNG/JPEG/WebP screenshots are stored in SQLite; admins can review or dismiss them. Dictation is an explicit browser microphone action and uses the browser's configured speech-recognition service. No AI provider is configured: the app does not send source code to a model, generate or apply patches, run commands, rotate credentials, or deploy changes. Review statuses record triage only. Do not include passwords, API keys, or unnecessary customer data in a report.

The app loads several presentation libraries from public CDNs, so those assets require an internet connection. Invoice creation, customer and item records, print layout, and optional WhatsApp/UPI links are available in the local app; payment processing is not included.

The PWA service worker caches only the app shell; it never caches API responses or account/billing data. The local installation is still bound to this computer. Sharing live data across computers requires a separately secured HTTPS host and a configured shared database; the desktop installer does not provide that hosting.
