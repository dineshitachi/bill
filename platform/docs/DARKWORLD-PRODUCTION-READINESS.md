# darkworld.website Production Readiness Checklist

Use this checklist before exposing darkworld.website to production users and again before major releases. It is based on the current repository, not a live-host inspection or penetration test. A code feature being present does not mean its production configuration or operation has been verified.

## Status key

- **Present** — implementation or documented control exists in the repository; still verify the deployed configuration.
- **Partial** — some controls exist, but important work or production verification remains.
- **Not verified** — requires an environment, operational evidence, or test not available from source inspection.
- **Not implemented** — the current platform documentation or code does not provide the capability.

## Go-live checklist

| # | Readiness item | Current evidence | Status | Go-live action |
|---|---|---|---|---|
| 1 | Remove test/demo data | The platform uses operator-provisioned tenant schemas. The repository also contains local-app databases, JSON data, and billing files; their ownership and production status cannot be determined from filenames alone. | Not verified | Inventory each environment and tenant with its owner. Remove only confirmed disposable records using an approved, backed-up cleanup procedure. Do not delete the root SQLite/JSON/PDF/CSV files or a production tenant merely because they might be test data. Verify the production tenant contains only approved business records. |
| 2 | Keep API keys and secrets private | The deployment passes provider credentials as server environment variables; the tenant API key is documented as shown once and stored hashed. | Partial | Confirm production secrets exist only in the deployment secret store/protected `.env`, never in `NEXT_PUBLIC_*`, client bundles, source control, URLs, screenshots, or logs. Rotate any key that was exposed. Verify provisioning output is handled as a secret and access is restricted. |
| 3 | Protect administrator routes | Middleware applies role gates to API path groups, and many handlers also call session/role/permission guards. | Partial | Review every route, including new and nested routes, for handler-level authorization. Verify admin-only actions reject unauthenticated, staff, and customer sessions with 401/403. Middleware path rules are defense in depth, not a substitute for resource-level checks. |
| 4 | Verify authentication and permissions | Sessions use signed HTTP-only, SameSite cookies; tenant and user state/role are rechecked by server auth helpers. Named permissions are available. | Partial | Test login/logout, expiry/refresh, disabled users, role changes, tenant maintenance/disablement, customer portal scoping, and each role/permission combination. Confirm every object lookup is scoped to the authenticated tenant and authorized user. |
| 5 | Secure database access and data | PostgreSQL is on the internal Compose network; app access uses a restricted DB role; sensitive fields are application-encrypted. | Partial | Verify production credentials and grants, private network/firewall rules, TLS where required by the host, encrypted volumes/backups, least privilege, migration access, secret rotation, backup retention, and a successful isolated restore. Ensure tenant schema selection cannot be client-controlled. |
| 6 | Validate all user input | Zod validation and bounded request parsing are used in many API routes. | Partial | Audit every route and every field, including query/path parameters, sizes, numeric bounds, enums, uploaded content, and provider responses. Reject unexpected or malformed input with safe client errors. Add regression tests for boundary and invalid cases. |
| 7 | Apply API rate limits | Nginx has per-IP request and connection limits; some application endpoints have local limits. The login throttle and some route counters are process-local. | Partial | Test limits at the edge and application layers. Before running multiple app instances, move security-relevant counters to shared storage. Verify trusted-proxy client IP handling, `429` responses, burst behavior, and limits on login, provisioning, exports, uploads, and expensive integrations. |
| 8 | Test file uploads | The company logo and agent screenshot flows validate supported image types and size bounds; the agent request body is bounded. | Partial | Test empty, oversized, malformed, spoofed MIME, invalid base64, and unsupported-format uploads; confirm temporary data is bounded and not publicly accessible. Check image decoding/resizing and error behavior. Verify upload limits also exist at the proxy and deployment layers. |
| 9 | Handle API errors safely | Shared JSON error helpers exist; several provider/payment paths return generic client errors and log server-side details. | Partial | Exercise validation, auth, database, timeout, and provider failures. Ensure responses never include stack traces, SQL, tokens, filesystem paths, or raw provider secrets. Use consistent status codes and a request/correlation ID; keep logs private and redact sensitive fields. |
| 10 | Remove debug logging | No `console.log` or `console.debug` calls were found in `platform/src`; intentional `console.error` calls remain for server failures. | Partial | Repeat the check against the production build and deployment logs. Keep actionable errors, but ensure logged objects cannot contain credentials, request bodies, payment details, customer PII, or tokens. Disable verbose framework/database logging in production. |
| 11 | Hide sensitive errors | Auth and several integrations return generic errors; diagnostic text has redaction helpers. | Partial | Verify all public error paths, including Next.js error boundaries and reverse-proxy 4xx/5xx pages, reveal no internal details. Confirm redaction is applied before telemetry/log export and test it with representative secret/PII patterns. |
| 12 | Test mobile layouts | Mobile acceptance is not established by this source inspection. | Not verified | Test key workflows at narrow phone/tablet widths and on supported browsers: sign-in, checkout, inventory, customer lookup, invoice preview/print, settings, and dialogs. Check keyboard access, touch target size, overflow, and orientation. |
| 13 | Test slow and unstable networks | The app has loading/error recovery behavior, but network-condition acceptance is not established here. | Not verified | Use browser throttling and offline/latency simulation to test reads, writes, retries, duplicate submissions, timeouts, and recovery. Confirm invoice/payment writes are not reported successful until committed; communicate that the shared platform does not support offline checkout. |
| 14 | Verify payments and webhooks | Invoice payments are recorded in the tenant database. The platform documentation says payment-gateway settlement is not enabled; no inbound payment webhook route was identified in the current API route search. | Not implemented | If accepting online payments, integrate an authorized provider. Verify webhook signatures against the raw request body, reject invalid/replayed events, enforce idempotency, correlate provider event/payment/invoice IDs, reconcile amounts/currency/status server-side, and acknowledge only after durable processing. Test duplicate, delayed, out-of-order, invalid-signature, and provider-retry events in staging. Until then, do not claim that provider settlement or webhook processing is supported. |
| 15 | Try to break the app safely | Automated tests exist, but a production security assessment has not been performed as part of this checklist. | Not verified | Test only an isolated staging environment with synthetic data and explicit authorization. Cover authentication/authorization bypass, cross-tenant access, IDOR, malformed input, upload limits, rate-limit behavior, session handling, and error disclosure. Run dependency/build checks and a documented independent security assessment before handling real customer/payment data. Never run destructive or high-volume tests against production. |

## Release gate

Do not treat this checklist as a certification. Before launch, an owner should record the date, environment, evidence link, and pass/fail result for each item. Resolve all **Not implemented** items needed by the product scope, and do not mark **Not verified** items complete without staging or production-operations evidence. Have a separate reviewer approve the final release.

At minimum, block launch if production secrets are exposed, test data is mixed with real tenant data, any authorization or cross-tenant test fails, database recovery has not been demonstrated, or payment behavior is represented inaccurately.

## Suggested execution order

1. Inventory the production environment, secrets, tenants, and data; take and verify a protected backup before any cleanup.
2. Complete route/role/tenant authorization checks and input/upload validation tests.
3. Configure shared rate limits if using more than one app instance; verify API error and log redaction.
4. Complete mobile and slow-network acceptance testing on staging.
5. Decide whether online gateway/webhook support is in scope. If so, implement and test it before representing payments as automatically settled.
6. Run the authorized staging security assessment, resolve findings, and capture release evidence.
